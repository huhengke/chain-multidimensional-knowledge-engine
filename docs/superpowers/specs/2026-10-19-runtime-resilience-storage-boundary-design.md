# 知识数据推理脑：运行韧性与存储边界设计

## 状态与范围

本规格已于 2026-10-19 审阅确认并进入实现。它只改变知识数据推理脑的查询运行时、统一 Agent 的运行控制，以及与知识索引直接相关的存储边界。结构化数据推理脑、时空记忆推理脑的事实库、数据契约、权限和业务查询逻辑不迁移、不重建。

本轮已实现：知识查询索引的显式就绪标记、版本化只读快照及其清单校验、查询投影与完整治理/拓扑状态分离加载、后台候选工作区构建与原子激活、普通聊天模型保存不清空知识工作区、90 秒墙钟时限、三类 Agent 的暂停/撤回，以及运行中只轮询单个运行状态、终态才刷新完整会话。已通过快照恢复、旧快照无资料重放升级、三脑运行轨迹及暂停/撤回的定向回归；真实医书的冷热态时延与生产并发仍需在部署环境测量。

本轮处理四个已确认问题：

1. 服务重启后，知识脑会回放全部历史资料并长时间持有全局锁，前台查询被阻塞。
2. 即使资料没有变化，查询仍通过完整内容形状计算索引签名，造成不必要的 O(N) 遍历。
3. 已发送问题不能暂停，前端还会高频拉取整段会话。
4. 保存普通对话模型配置会清空知识工作区，导致模型页面保存等待索引重建；流式模型调用没有真正的总时限。

## 现状盘点

活动数据库为 `.runtime/standalone/platform/platform.sqlite3`，约 323 MiB。它不是“只存参数”的配置库：

| 类别 | 当前规模 | 作用 |
| --- | ---: | --- |
| `knowledge_cache` | 约 213 MiB | 已解析、分段、索引、图谱和 Wiki 的可再生运行缓存 |
| `records` | 约 54 MiB | 资产、任务、复核、会话、运行记录、拓扑投影等元数据及部分投影 |
| `pdf_page_cache` | 约 33 MiB | PDF 页面解析与 OCR 复用缓存 |
| `model` 记录 | 约 1.9 KiB | 模型名称、地址、用途、超时、启停和密钥引用 |

原始资料不放在 SQLite 中，而是按 SHA-256 保存在同目录的 `objects/`。模型记录也不保存明文 API Key，只持有单独加密凭据的引用。

因此，单纯将模型参数从 SQLite 移至 YAML/JSON，几乎不会降低占用或消除查询瓶颈，反而会损失后台编辑、审计和并发一致性。真正需要分离的是可再生的索引和解析工件。

## 方案比较与结论

### 方案 A：仅把模型配置改为 YAML/JSON

文件适合部署默认值，但不能处理后台多次修改、审计、版本回退和运行时一致性；同时只影响约 1.9 KiB 数据，不解决查询阻塞。**不采用。**

### 方案 B：继续让 SQLite 承载全部缓存，并仅缩短锁

改动较小，但大向量、PDF 缓存、拓扑投影仍与元数据混在一起；重启后仍需要回放资料构建内存查询结构。**不采用。**

### 方案 C：配置、元数据、索引工件分层，查询使用版本化只读快照

采用此方案。

- YAML/JSON 是非敏感部署基线和可导入导出的模型配置文件，不保存 API Key。
- SQLite 保留轻量、事务性元数据：资产标识、发布/复核状态、当前配置版本、运行记录、审计、工件清单和密钥引用。
- 模型的运行态编辑继续写入 SQLite，并可从 YAML 基线初始化；普通聊天模型保存只更新自身记录和审计。
- 原始文件继续保存在对象目录。
- 解析结果、倒排索引、双时间轴、星团路由、向量矩阵和拓扑投影按知识索引版本写入外部工件目录。SQLite 仅保存工件版本、路径、校验和、状态与激活指针。

这既不把动态运行态退化成手工改文件，也明确了配置、元数据、原文和可再生索引的边界。

## 目标存储结构

每个知识所有者和索引版本拥有一个不可变工件目录：

```text
.runtime/standalone/knowledge-artifacts/
  <owner-sha256>/<revision>/
    manifest.json
    state.json              # 完整治理与拓扑状态，仅画布/治理按需加载
    query-state.json        # Agent 默认映射的轻量查询投影
    query-index.json        # 路由元数据、词项计数与向量位置
    lexical.sqlite3         # 不可变 token -> unit posting，只读按词访问
    unit-vectors.npy
    cluster-vectors.npy
```

`state.json` 保存完整受治理的文档、单元、证据、拓扑、双时间索引、星团与路由投影，供智慧树画布、复核和纠偏按需读取；`query-state.json` 仅保存 Agent 检索需要的文档/单元/证据/发布权限、双时间索引与轻量路由字段。`query-index.json` 保存候选索引元数据、词项计数和向量位置；高基数的 token posting 单独存入 `lexical.sqlite3`，查询时只按本次问题的少数词项只读访问，不在热工作区反序列化为 Python set 图。`manifest.json` 记录生成来源、资料版本集合、运行时空间标识、各文件 SHA-256、单元/星团/时间桶计数和生成时间。数值向量使用不含对象反序列化的 NPY 格式。禁止使用 pickle 或从工件反序列化可执行代码。

稳定查询工作区只保留 NPY 查询矩阵；单元和向量留痕中的重复 Decimal 字符串向量在快照写入后释放，保留向量维度、来源引用、星团原型、证据和拓扑关系。这样不影响检索、树图或审计，却避免同一向量在运行内存中保留多份副本。

SQLite 中新增或扩展的记录只保存 `revision`、`status`、`manifest_digest`、激活时间和失败原因。当前 `knowledge_cache`、`pdf_page_cache` 作为迁移期只读兼容来源；本轮不清除旧缓存、旧资料或医书。

## 索引与查询生命周期

### 导入、复核与索引生成

1. 导入、发布复核通过、内容时间纠偏或 embedding 空间迁移会创建候选 `revision`。
2. 后台根据固定的资料版本集合生成候选工件，完成后校验清单、数量、校验和、权限/发布状态和向量空间。
3. 校验成功后，以单次原子写入切换该所有者的 `active_revision`；失败则保留当前激活版本并记录失败原因。
4. 工件构建不占用前台查询锁。服务恢复优先映射有效 `query-state.json`、只读 `lexical.sqlite3` 与 NPY 矩阵；智慧树画布和治理请求才按需读取完整 `state.json`。schema 3 快照可在不重放原件、分块或 embedding 的情况下转为 schema 4：复用状态和 NPY 工件，只生成词项数据库及瘦身元数据，然后原子激活。缺少首个快照时兼容恢复才会从既有持久资产构建一次并生成快照。生产部署应在切流前由受控迁移任务预生成首个工件，避免把这一兼容路径留给首次提问。

### 查询

1. 查询读取当前 `active_revision` 的只读索引，创建的只是本次问题的轻量上下文：权限、树域、时间范围、星团候选、重排和模型调用。
2. 对不同问题复用同一份知识库快照。例如 `R42` 是“当前已发布资料的完整查询索引”，不是上一条问题的答案；它可以回答任意新问题。
3. 新版本 `R43` 构建期间，查询继续读取 `R42`。`R43` 完整校验后才一次性切换，绝不让查询读到半生成的树、星团或向量。
4. 查询只比较常数时间的 `active_revision`，不再通过遍历所有知识单元计算签名。只有索引版本变化才重新映射本地只读工件。
5. 双时间轴、文字倒排、树域和星团共振仍先做候选裁剪；向量与重排只用于需要的候选集，不允许退化成每个问题全库重建或全量扫描。

这里的“独立查询”与“独立工作区重建”必须区分：常规 Agent 为每个问题独立执行路由和模型调用，但共享只读语料索引。为每个问题重复装载数万单元、向量矩阵与星团，会在线程并发时成倍消耗 CPU 和内存，且不会提升隔离性或正确性。

## 模型配置边界

1. `config/model-profiles.yaml` 提供非敏感的部署基线：供应商地址、模型名、用途、默认超时与能力声明。它可被导入、导出和版本管理。
2. SQLite 中的运行态配置保留当前启用配置、显式覆盖、配置修订和审计；密钥仅以加密的引用保存，可在生产环境替换为外部密钥服务。
3. 普通聊天模型的修改只保存配置和审计，不得清空 `KnowledgeWorkspace`、不得触发索引构建。
4. 只有知识脑的 embedding/rerank 空间发生实质变化时才允许创建受控索引迁移任务；新空间工件验收前，旧索引继续提供查询。

## 会话暂停、撤回与严格时限

运行控制作为统一 Agent 的标准能力实现，并为三个专脑工作台提供同一运行状态协议。

1. 发送问题时，先持久化用户消息与 `running` 运行记录，再启动可追踪的后台任务。
2. “暂停本次运行”取消尚在等待的检索、重排或模型 HTTP 请求，将运行置为 `paused`，保留问题、已完成步骤、耗时和证据；不保存半截正式回答。
3. 暂停后提供“重新运行”和“撤回问题”。重新运行复用同一问题创建新的运行版本；撤回只允许作用于未完成或已暂停的本次问题，并删除该问题与关联运行，不影响其他会话。
4. 对不能被上游立即中断的线程计算，暂停立刻使结果失效，迟到结果不得写回会话。
5. 前端使用轻量运行状态端点轮询；终态后才刷新会话内容，不再每 900ms 重拉完整历史。
6. 知识脑模型调用用整个协程的 90 秒墙钟时限包裹，不因 SSE 心跳重复计时。超时、暂停、失败和完成都必须进入终态。

## 可观测性与验收

运行记录必须分别报告：工件版本、索引映射耗时、文字/时间/星团候选耗时、embedding、重排、模型首 token、模型生成、总时长、取消原因和超时阶段。

验收标准：

1. 服务器重启后，已激活工件可立即映射并接受查询，不重放所有历史资料；查询开始不被后台候选版本构建阻塞。
2. 资料不变时，连续查询不会扫描全体单元来计算索引签名；监控中能看到版本复用。
3. 更新资料后，旧版本持续可查询；新版本只在完整校验后激活。
4. 暂停、重试、撤回分别有正确的会话、审计和迟到结果抑制行为。
5. 对话模型配置保存不因知识索引构建等待；embedding/rerank 变更显式进入迁移任务。
6. 长连接模型即使持续发送 SSE 心跳，也会在 90 秒总时限进入终态。
7. 现有医书的原始文件、SHA-256、文档 ID、发布状态、权限、内容时间锚点、树和星团关系保持不变；不要求重新导入。

## 迁移与回退

1. 先从现有持久化资产和缓存生成候选工件，校验后才写入激活指针；旧快照先转换为查询投影与矩阵格式，不因工件格式升级而重新嵌入或重新导入资料。
2. 新读取路径在找不到有效工件时只读兼容旧缓存，并创建受控的首个快照；当前兼容恢复保留一次性全量构建能力以保护没有任何快照的存量安装。生产切流前应完成预热，以避免首次提问承担该成本。
3. 上线初期保留 SQLite 旧缓存和原始对象，工件版本可回退到前一已验证版本。
4. 旧缓存的物理清理不属于本规格的自动动作，必须在备份、保留周期和用户明确确认后以单独维护任务执行。
